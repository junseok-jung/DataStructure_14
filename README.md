# 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교 분석

## 1. 실험 개요
본 실험에서는 무작위 정수 데이터($n = 1,000, 2,000, 4,000, 8,000, 16,000, 20,000$)에 대하여 **힙 정렬(Heap Sort)**, **병합 정렬(Merge Sort)**, 그리고 세 가지 피벗 선택 방식(First, Random, Median-of-Three)을 적용한 **퀵 정렬(Quick Sort)**을 수행하고, **숫자 비교 횟수**, **실행시간(ms)**, **추가 메모리 사용량(Bytes)**을 측정하여 비교·분석하였다.

---

## 2. 데이터 크기 증가에 따른 비교 횟수 변화 분석

| 데이터 크기 ($n$) | Heap Sort | Merge Sort | Quick (First) | Quick (Random) | Quick (Median3) |
| :---: | :---: | :---: | :---: | :---: | :---: |
| 1,000 | 16,847 | 8,707 | 10,816 | 11,185 | 10,142 |
| 2,000 | 37,691 | 19,412 | 24,885 | 24,610 | 22,318 |
| 4,000 | 83,384 | 42,825 | 54,612 | 55,104 | 49,186 |
| 8,000 | 182,765 | 93,651 | 120,148 | 119,422 | 107,540 |
| 16,000 | 397,532 | 203,304 | 262,410 | 264,890 | 233,980 |
| 20,000 | 509,984 | 260,918 | 338,125 | 336,490 | 299,712 |

1. **$O(n \log_2 n)$ 증가 추세 확인**:
   - 모든 알고리즘에서 데이터 크기 $n$이 2배 증가할 때 비교 횟수는 약 $2.15 \sim 2.25$배씩 증가하여 이론적인 $O(n \log_2 n)$의 로그 선형 비례 관계를 정확히 따른다.
2. **알고리즘 간 비교 횟수 순서 (`Merge Sort < Quick (Median3) < Quick (First/Random) < Heap Sort`)**:
   - **병합 정렬**: 두 정렬된 부분 배열에서 한 번의 비교마다 반드시 하나의 원소 위치가 확정되므로 약 $n \log_2 n - 1.26n$ 회의 가장 적은 비교가 발생한다.
   - **퀵 정렬**: 평균적으로 약 $1.39 n \log_2 n$(First/Random) 및 약 $1.19 n \log_2 n$(Median3) 회의 비교가 발생하여 병합 정렬보다 다소 많지만 힙 정렬보다는 훨씬 적다.
   - **힙 정렬**: 초기 최대 힙 구성 과정에서 약 $1.88n$ 회의 비교가 발생하고, 이후 최댓값을 리프 노드와 교환하여 `sift_down`으로 힙 속성을 복구할 때마다 트리의 바닥 부근까지 내려가며 매 단계 **1) 좌우 자식 간 비교**와 **2) 부모와 큰 자식 간 비교**의 총 2회 비교가 수행된다($\approx 2 n \log_2 n$). 따라서 병합 정렬 대비 약 **1.95배** 많은 비교가 발생한다.

---

## 3. 힙 정렬, 병합 정렬, 퀵 정렬의 실행시간 차이

1. **퀵 정렬이 가장 빠른 이유 (Cache Locality 및 낮은 오버헤드)**:
   - 병합 정렬보다 비교 횟수가 약 15~30% 더 많음에도 실제 실행시간은 `Quick (Median3)`와 `Quick (First)`가 가장 짧다($n=20,000$ 기준 `1.423ms` vs 병합 정렬 `2.012ms`).
   - 이는 퀵 정렬이 인접한 배열 인덱스를 순차적으로 스캔하여 **CPU 캐시 지역성(Spatial Locality)**이 매우 뛰어나고, 병합 정렬처럼 임시 배열에 데이터를 복사(`arr -> temp -> arr`)하는 추가 메모리 이동 비용이 없기 때문이다.
2. **병합 정렬의 실행시간 특성**:
   - 비교 횟수는 가장 적으나, 매 병합 단계마다 동적 할당된 임시 배열과 원본 배열 간의 데이터 복사 연산이 발생하여 퀵 정렬보다 실행시간이 다소 길다.
3. **힙 정렬이 가장 느린 이유**:
   - 첫째, `sift_down` 과정에서 매번 좌·우 자식 비교와 부모 비교가 모두 일어나 비교 횟수 자체가 가장 많다.
   - 둘째, 배열 인덱스 접근이 `parent` $\rightarrow$ `2 * parent + 1` 형태로 건너뛰며 일어나기 때문에 데이터가 커질수록 **캐시 미스(Cache Miss)**가 빈번하게 발생한다.
   - 셋째, 이미 작은 값인 리프 노드를 루트로 끌어올린 뒤 다시 바닥까지 내려보내는 불필요한 이동이 반복된다.

## 4. 세 정렬 알고리즘의 메모리 사용량 차이

1. **힙 정렬 ($32\text{ Bytes}$, $O(1)$)**:
   - 별도의 힙 배열을 생성하지 않고 입력 배열 자체를 최대 힙으로 구성하는 **제자리 정렬(In-place Sort)**이며, `sift_down` 역시 반복문으로 구현되어 데이터 크기 $n$과 무관하게 일정한 지역 보조 변수 공간($32\text{ Bytes}$)만 사용한다.
2. **퀵 정렬 ($816 \sim 2,016\text{ Bytes}$, 평균 $O(\log n)$)**:
   - 추가 배열은 필요 없으나 분할 정복을 위한 **재귀 호출 스택**이 사용된다. $n = 20,000$에서도 최대 재귀 깊이가 $31 \sim 42$ 수준에 불과하여 약 $1.5 \sim 2.0\text{ KB}$의 적은 메모리만 소모한다.
3. **병합 정렬 ($4,528 \sim 80,768\text{ Bytes}$, $O(n)$)**:
   - 병합 단계에서 정렬 결과를 담기 위한 크기 $n$의 임시 배열(`n * sizeof(int)`)이 필수적이므로, 데이터 크기에 정비례하여 메모리 사용량이 급격히 증가한다($n=20,000$일 때 임시 배열 $80,000\text{ Bytes}$ + 재귀 스택 $768\text{ Bytes} = 80,768\text{ Bytes}$).

---

## 5. 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

1. **Median-of-Three (`Quick (Median3)`)**:
   - 첫 번째, 중간, 마지막 원소 중 중앙값을 피벗으로 선택하므로 편향 분할(Skewed Partition)이 발생할 확률이 크게 줄어든다.
   - 피벗 선택 시 3회의 값 비교가 추가되지만, 분할 균형이 좋아져 전체 재귀 깊이와 총 비교 횟수가 세 방식 중 **가장 적고($n=20,000$에서 299,712회)**, 실행시간(**1.423ms**)과 스택 메모리(**1,488 Bytes**) 모두 가장 우수하다.
2. **첫 번째 원소 선택 (`Quick (First)`)**:
   - 입력 데이터가 무작위 정수이므로 평균적인 분할 성능은 무작위 피벗과 유사하며, `rand()` 호출 비용이 없어 실행시간은 `Quick (Random)`보다 약간 빠르다. (단, 이미 정렬된 데이터가 입력될 경우 $O(n^2)$ 최악의 성능을 보이는 한계가 있다.)
3. **무작위 원소 선택 (`Quick (Random)`)**:
   - 비교 횟수와 재귀 깊이는 `Quick (First)`와 거의 동일하지만, 매 분할마다 난수 생성 함수(`rand()`)와 나머지 연산을 수행하는 오버헤드로 인해 실행시간이 세 가지 피벗 방식 중 가장 길다($n=20,000$에서 `1.724ms`).

## 6. 시간 복잡도 및 공간 복잡도 비교 요약

| 알고리즘 | 최선 시간 복잡도 | 평균 시간 복잡도 | 최악 시간 복잡도 | 공간 복잡도 (추가 메모리) | 안정 정렬 여부 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Heap Sort** | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(1)$ | 불안정 (Unstable) |
| **Merge Sort** | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n)$ | 안정 (Stable) |
| **Quick (First)** | $O(n \log n)$ | $O(n \log n)$ | $O(n^2)$ | 평균 $O(\log n)$ / 최악 $O(n)$ | 불안정 (Unstable) |
| **Quick (Random)** | $O(n \log n)$ | $O(n \log n)$ | $O(n^2)$ | 평균 $O(\log n)$ / 최악 $O(n)$ | 불안정 (Unstable) |
| **Quick (Median3)** | $O(n \log n)$ | $O(n \log n)$ | $O(n^2)$ | 평균 $O(\log n)$ / 최악 $O(n)$ | 불안정 (Unstable) |

## 7. 메모리 사용량의 측정 방법과 계산 기준

공통 비용인 원본 데이터 배열(`sizeof(int) * n`)은 제외하고, 각 정렬 알고리즘이 수행되는 동안 점유하는 **최대 추가 메모리(Peak Auxiliary Memory)**를 다음 기준으로 측정하였다.

1. **힙 정렬 (`Heap Sort`)**:
   - 반복문 기반의 제자리 정렬로 구현하여 재귀 호출 스택이 누적되지 않는다.
   - `run_heap_sort` 및 `sift_down` 내부에서 동시에 활성화되는 지역 보조 변수(`i`, `temp`, `parent`, `left`, `right`, `largest_child` 등 정수형 변수 6개 + 포인터 1개)의 크기인 **`32 Bytes`**로 산정하였다.
2. **병합 정렬 (`Merge Sort`)**:
   - 동적 할당된 임시 배열 크기 `n * sizeof(int)` ($4n\text{ Bytes}$)에 런타임에 측정된 최대 재귀 호출 깊이(`max_depth`) $\times$ 함수 스택 프레임 크기(`MERGE_FRAME_BYTES = 48 Bytes`: 매개변수 포인터, 인덱스 변수 `left`, `mid`, `right`, 반환 주소 등)를 합산하여 계산하였다.
   - $\text{Memory(Bytes)} = 4n + (\text{max\_depth} \times 48)$
3. **퀵 정렬 (`Quick Sort`)**:
   - 제자리 분할을 수행하므로 별도의 동적 배열은 없으며, 재귀 호출 시마다 현재 깊이(`depth`)를 전달하여 실행 중 도달한 **최대 재귀 깊이(`max_depth`)**를 직접 측정하였다.
   - 측정된 `max_depth`에 재귀 호출 1회당 스택 프레임 크기(`QUICK_FRAME_BYTES = 48 Bytes`: 매개변수, 지역 변수 `pivot`, `i`, `j`, 반환 주소 등)를 곱하여 계산하였다.
   - $\text{Memory(Bytes)} = \text{max\_depth} \times 48$
